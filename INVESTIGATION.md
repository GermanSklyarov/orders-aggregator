# Диагностика до исправлений

Проверено 10.11.2026 на исходном коде. Это диагностический запуск, не финальная
сдача: `result.json` не создавался. Исходные 27 тестов и `npm run typecheck` прошли.

## Окружение и исходные данные

Образ `orders-mock:3` загружен из приложенного arm64-архива. Из-за TLS timeout
Docker Hub PostgreSQL запущен из уже имеющегося `postgres:16-alpine` через
временный `/tmp/orders-task-compose.yml`; исходный Compose не менялся.
Зависимости установлены через `npm ci`, применена `001_init.sql`.

API `/customers/c_7` вернул `Europe/Berlin`. Полный проход: 52 страницы,
5030 уникальных заказов, 140 заказов c_7; 1177 заказов не имеют обоих новых
полей. Встречаются строковые проценты и суммы, время без зоны (по соглашению UTC).
Все 5030 записей приняты исходным `/sync`, invalid/stale = 0.

`test/fixtures/c7.json` содержит реальные 140 заказов c_7 и тела 92 вебхуков
в порядке поступления. Вебхуки отправлены командой README через диагностический
HTTP-прокси на :3001, который записывал тела/ответы и передавал запросы сервису
на :3000. Все 92 ответа — HTTP 200 (60 updated, 32 stale). Прокси влияет на
планирование конкурентных запросов; порядок завершения не гарантирован.

## DST — подтверждённая причина расхождения gross/total

Исходный TotalsService.daily использует смещение на момент запроса (в ноябре
UTC+1) для всех дат. В Берлине 29.03.2026 в 01:00Z смещение меняется на UTC+2.
Локальный день 29 марта: [28.03 23:00Z, 29.03 22:00Z), 23 часа.

Примеры оплаченных заказов после синхронизации:

| Заказ | createdAt UTC | Старый день | Правильный день | gross, ₽ |
|---|---|---|---|---:|
| o_02357 | 29.03 22:40:08 | 29.03 | 30.03 | 9306 |
| o_02448 | 30.03 22:40:44 | 30.03 | 31.03 | 1823 |
| o_02547 | 31.03 22:40:06 | 31.03 | 01.04 | 4999 |

Независимая проверка группировала исходные даты через Intl в Europe/Berlin.
Суммы до вебхуков:

| День марта | Ответ исходного сервиса, ₽ | Правильный gross, ₽ |
|---|---:|---:|
| 27 | 24736 | 24736 |
| 28 | 47995 | 47995 |
| 29 | 58871 | 49565 |
| 30 | 52201 | 59684 |
| 31 | 43576 | 40400 |

27–28 марта совпадают; после DST суммы перераспределяются между днями и границей
периода. При запуске летом ошибка затронет дни до перехода вместо дней после него.

## Денежное преобразование

`Math.floor(rub * 100)` теряет копейку на реальных amountPaid:
o_02225: 4549.23 → 454922 вместо 454923; o_02244: 4099.44 → 409943 вместо
409944; o_02448: 1276.1 → 127609 вместо 127610; o_05008: 2284.99 → 228498
вместо 228499. Это отдельная подтверждённая проблема для net. В исследованной
выборке gross имеет целые рубли, а старый total не использовал amountPaid,
поэтому потеря копеек не объясняет исходное расхождение total.

## Обновления — подтверждённая гонка

После доставки вебхуков сравнили БД с максимальным updatedAt для каждого id
среди API и всех записанных событий. Обнаружены три устаревшие записи:

| Заказ | updatedAt в БД | Максимальный принятый updatedAt |
|---|---|---|
| o_02455 | 31.03 02:28:24Z | 31.03 03:28:24Z |
| o_02600 | 01.04 15:42:43Z | 01.04 16:42:43Z |
| o_02559 | 01.04 03:53:40Z | 01.04 04:53:40Z |

У o_02455 старое событие содержит amountPaid=8638.2, новое — 6430.66:
риск завышения net на 2207.54 ₽ за 31 марта. Исходный сервис вообще не сохраняет
эти поля, но устаревший updatedAt в БД доказывает откат версии. У o_02559
сохранён paid вместо более нового refunded (вне запрошенного периода).
Причина в коде: отдельные SELECT и безусловный UPSERT. Даже одинаковые
конкурентные события несколько раз получают updated вместо stale.

В этом конкретном запуске откат версии не изменил gross за 27–31 марта.
После вебхуков старые total: 24736, 58233, 43964, 52201, 44064.
При выборе максимальной версии и правильной таймзоны gross:
24736, 58233, 34658, 59684, 35401. Изменения относительно синхронизации
вызваны реальными сменами статусов; их нельзя путать с ошибкой DST.

Эталон net после всех максимальных версий, в копейках:
1985551, 5429119, 3195965, 4901076, 2978755.
Если использовать старый floor для этих amountPaid, потери по дням:
2, 2, 1, 0, 1 копейка соответственно.

Отдельный отчёт платёжной системы не предоставлен. Выводы основаны на
контракте задания, реальных телах API/вебхуков, снимке БД и независимом
пересчёте, а не на предположении, что все различия вызваны одной ошибкой.

## Воспроизведение тестами до исправления

`npm test -- test/regressions.test.ts` на исходной реализации: 5 из 5 тестов
упали. Подтверждены потеря копеек, неправильный gross в ноябре, откат версии
при записи прямо в репозиторий, отсутствие новых итогов и несколько created
для конкурентных одинаковых событий. После исправления эти же проверки
проходят; дополнительные тесты проверяют границы суток и конкурентный sync.
