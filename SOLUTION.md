# Решение

Финальный чистый прогон выполнен 10.11.2026. Точное тело HTTP-ответа сохранено
в `result.json` в корне проекта, без ручного формирования или перезаписи сумм.
Диагностический цикл исходного сервиса выполнен до исправлений. Подробные
наблюдения, суммы и реальные примеры — в `INVESTIGATION.md`; сохранённая
выборка API и вебхуков — в `test/fixtures/c7.json`.

## Подтверждённые причины

1. Для Europe/Berlin использовалось сегодняшнее смещение вместо смещения
   на дату заказа. Это объясняет совпадение gross 27–28 марта и расхождение
   29–31 марта при зимнем времени построения отчёта. Ошибка не в SQL-границах
   выборки и не в перечислении календарных дат.
2. `floor(rub * 100)` теряет копейки на реальных amountPaid из-за float.
   Исходный total эти поля не использовал, поэтому это отдельная ошибка,
   значимая для новой статистики net, а не причина старого gross.
3. Конкурентные вебхуки действительно откатывали версии: обнаружено три
   несовпадения updatedAt в БД с максимальной доставленной версией. Для
   o_02455 это затрагивает оплату 31 марта, но не сумму до скидки.

## Изменения и решения

- ExternalOrder / OrdersService.normalize принимают и проверяют процент и
  оплату. Старый формат без обоих полей означает отсутствие скидки; неполная
  пара отклоняется. Это подтверждено реальными 1177 старыми заказами API.
- Новая миграция, Order/Row/fromRow/save сохраняют discount_percent (NUMERIC)
  и amount_paid_kop (BIGINT). Процент хранится для полноты версии, net берётся
  исключительно из фактического amountPaid. Несоответствие оплаты вычисленному
  проценту не исправляется автоматически. Частичная оплата не моделируется;
  amountPaid должен лежать в пределах 0..amount, процент — 0..100.
- TotalsService.daily использует смещение в момент createdAt. Сохраняется
  расширенная SQL-выборка и группировка в сервисе, без новой библиотеки времени
  и без изменения смысла даты заказа. Возвращаются total=gross, net, discount;
  суммы сначала складываются/вычитаются в копейках, потом переводятся в рубли.
- toKop разбирает десятичное представление без умножения float. Строки не
  преобразуются в number перед выделением копеек; поддержана экспоненциальная
  запись. Существующая политика 10.999 → 1099 сохранена. Пустые, шестнадцатеричные,
  отрицательные и неограниченные суммы отклоняются; проверяется безопасный
  целочисленный диапазон и переполнение дневных итогов.
- Защита версий перенесена в OrdersRepository.save. Сначала INSERT ON CONFLICT
  DO NOTHING RETURNING id, затем, только при конфликте, UPDATE WHERE
  updated_at < incoming RETURNING id. Условие и запись UPDATE атомарны под
  блокировкой PostgreSQL. Отсутствует разрыв SELECT → безусловная запись.
  Два оператора сохраняют точный created/updated/stale без зависимости от xmax
  и других внутренних полей PostgreSQL. Повтор/равная версия возвращает stale.
  Сервис не поддерживает конкурентное удаление заказов; этого нет и в исходном API.
- Интерфейс OrdersApi и сигнатура createContainer(db, api) не менялись.

## Оставшиеся ограничения

- Старая БД уже потеряла поля скидок: миграция заполняет gross=net, процент=0.
  Повтор равной версии остаётся stale по контракту. Такая миграция сохраняет
  старую семантику, но НЕ восстанавливает достоверный исторический net.
  Для обновления существующей установки нужен отдельный контролируемый импорт;
  для задания выполнен чистый запуск, поэтому это ограничение не относится
  к сохранённому финальному result.json.
- updatedAt сравнивается с точностью JavaScript Date (миллисекунды). Субмиллисекундные
  версии в исследованных данных не обнаружены; при появлении потребуется иной
  формат версии. Равное время с отличающимся телом остаётся stale.
- Таймзона клиента кешируется без срока действия. Исторические изменения
  таймзоны клиента и paidAt в контракте отсутствуют; статистика остаётся по createdAt.
- Отдельно замечены не относящиеся к исправлению проблемы: некоторые невалидные
  даты запроса (например 2026-13-01) дают 500, HTTP-клиент не имеет собственного
  покрытия ретраев, успешное завершение на повторном курсоре может скрыть проблему
  upstream. Не включены в этот минимальный патч.
- При наличии времени: стратегия восстановления скидок в старой БД, тесты
  HTTP-клиента/ошибок upstream, ограничение диапазона отчёта, диагностика причин
  invalid при синхронизации, согласование точности и конфликтов версий с API.

Использован ИИ-ассистент Codex: чтение кода, запуск инфраструктуры, захват данных,
независимый пересчёт, написание и запуск регрессий. Причины сначала проверены на
исходном коде и реальном API; исправления внесены после фиксации доказательств.
